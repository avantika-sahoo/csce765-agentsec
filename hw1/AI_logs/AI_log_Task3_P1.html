    7. How to explain the outcomes

    Your explanation should be based on what your actual logs show, rather than assuming the small model will behave one particular way.

    If the direct marker is created

    Explain that the request originated in the control channel, so the model was explicitly asked to use the skill. The relevant security question then becomes whether the tool execution was permitted by the intended exec-policy.

    If the direct marker is blocked

    Explain that although the model received an explicit control-channel request and may have proposed the tool call, the authorization layer prevented execution. Therefore the model's proposal did not itself constitute execution authority.

    If the indirect marker is created

    This is the interesting case: the model treated an instruction originating in the data channel as actionable. Explain that the "run the marker" instruction originated inside retrieved external content rather than in your control message. Then show whether OpenClaw's execution policy nevertheless authorized the resulting tool call.

    If the indirect marker is not created

    That is completely acceptable—the assignment explicitly says the grade does not depend on the local model following the indirect instruction. Explain that the malicious instruction remained data, or that the model ignored it, or that an attempted tool call was blocked. The important evidence is the complete path from external content → model behavior → proposed call → authorization → execution.
